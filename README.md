# 郑州区域建筑三维模型 — 构建说明

由 `building/zheng_apart.shp`（建筑轮廓 + `high` 高度字段）与 `dem/dem.tif`（30 m DEM）
生成的城区三维几何模型，还原建筑分布格局、高程差异与街道走向。

## 2. 模型规格

```
建筑数            15,889 栋（源数据 15,889 个多边形，无一丢弃）
建筑三角面        333,952
地形三角面         97,082   (30 m DEM 网格，NoData 处不生成面)
总三角面          431,034
总顶点          1,293,102  (顶点按面展开不共享，故约 3 顶点/面)
建筑占地          8.36 km²   （真实米制；源 Shape_Area 求和 12.42 km² 含 Web Mercator 膨胀）
建筑高度 high     3.0 ~ 136.0 m，中位 21.5 m，均值 26.5 m
基底高程          69.5 ~ 138.2 m，中位 99.4 m（各栋取自身轮廓内地形渲染面的最高点）
屋顶高程          78.3 ~ 243.7 m
地形高程          64 ~ 139 m
轮廓内地形起伏    中位 2.45 m，p95 8.52 m，最大 36.19 m
被地形埋没的楼     0 栋（基底策略 = max 时自检保证）
```

每栋楼是**独立闭合体块**：屋顶受约束三角化 + 四面墙体，墙脚向下延伸 6 m 埋入地形，
因此在坡地上不悬空。颜色写在顶点色里（非贴图），按高度分 6 段渐变——
蓝→青→绿→黄→橙→红，对应 3 m 到 90 m+。

每个图元都带 **`POSITION` / `COLOR_0` / `NORMAL`** 三个属性。法线必须显式写入：
顶点按面展开不共享，逐面法线即精确的平直着色法线；缺法线时 three.js 的 `N·L` 恒为 0，
直射光与半球光全部失效，模型渲染成全黑（这是本文件的一个已知坑，见第 5 节）。

### 建筑基底策略 `BASE_MODE`

基底高程按**轮廓内密采样「地形渲染面」**得出（不是最近邻 DEM——两者在 30 m DEM 的陡坎处
能差几十米，见第 4 节）。采样点在轮廓内按 ≤8 m 间隔铺开，取到三个统计量后按环境变量选择：

| `BASE_MODE` | 基底取 | 效果 |
|---|---|---|
| **`max`（默认）** | 轮廓内地形最高点 | **楼永不沉入地形**；坡地上楼在低侧形成墙裙 |
| `centroid` | 轮廓内地形中位数 | 坡地上一半埋一半露，高度最不失真 |
| `min` | 轮廓内地形最低点 | 楼整体坐在低处，陡坎上会被地形吞掉 |

墙脚一律下探到「轮廓内地形最低点 − 2 m」，所以任何模式下都不会出现悬空缝。
换策略：`BASE_MODE=centroid python build_city.py`。

**为什么原来会沉**：旧版基底取「轮廓**边界顶点**的**最近邻** DEM 最小值」，两个缺陷叠加——
① 只采样边界、漏掉内部；② 用最近邻而不是插值面。本区 30 m DEM 存在真实陡坎
（相邻格高差 p90 = 5 m、p99 = 11 m、max = 29 m，1.04 % 的相邻格对差 >10 m），
一栋 10×36 m 的楼可能正跨在 29 m 的坎上，`min` 专挑低侧，整栋被吞。
实测旧版 **92.8 % 的楼基底低于其轮廓内地形最高点**，中位埋深 3.02 m，517 栋完全埋没。
改为密采样渲染面 + `max` 后 → **被埋 0 栋**。
对照图：[compare_base_min.png](compare_base_min.png)（旧） vs [compare_base_max.png](compare_base_max.png)（新）。

## 3. 坐标链路（关键）

```
shp 顶点 EPSG:3857  ──►  WGS84 经纬度  ──►  ECEF  ──►  局部 ENU 米制（原点 113.662169°E, 34.788899°N）
```

**逐顶点换算**，因此 `tileset.json` 里那个刚性的 ENU→ECEF 矩阵能**精确**还原每个顶点的
真实 ECEF 位置——不是近似贴合。

> ⚠️ 这一步不能省。EPSG:3857 在 34.79°N 处尺度膨胀 `1/cos(34.79°) = 1.2178`，
> 直接拿 3857 坐标当米用，建筑尺寸会虚大 22%，占地会虚大 48%。本模型已完全校正。
>
> 另一半坑：`zheng_apart.shp.xml` 里记录的字段表是**导出前的旧 schema**（写的是 `HEIGHT`），
> 实际 DBF 字段是 **`high`**。按元数据写代码会直接报错。

## 4. 垂直基准标定（重要发现）

DEM 是**正常高**（1985 国家高程基准），3D Tiles / Cesium 用**椭球高**，两者差一个
大地水准面差距 N。本模型用已有的 `白模/zhengzhou1` 逐栋标定：

```
(白模基底 − DEM) 中位数 = +4.41 m     n = 15,881 栋，IQR 2.82 ~ 6.55
```

该值已作为 `GEOID_OFF` 同时加到建筑与地形上（`build_stats.json` 的 `geoid_offset_applied`）。
如需改基准，设环境变量 `GEOID_OFF` 重跑即可。

### 附带发现：现有白模没有使用高度字段

逐栋实测 `白模/zhengzhou1` 的真实楼高（每个 GLB 顶点落到对应轮廓内取 z 跨度）：

| 建筑 | `high` 字段 | 白模实测楼高 |
|---|---|---|
| 豫茶新苑小区１号楼 | **136.0 m** | **10.0 m** |
| #15002 | **130.0 m** | 11.4 m |
| #6764 | **130.0 m** | 10.0 m |
| 郑州轻工业大学后勤保障服务中心 | 21.5 m | 10.0 m |
| #13437 | 14.5 m | 10.0 m |

全量统计：白模楼高**中位 10.02 m，63 % 落在 9.5–10.5 m**。
即现有白模把**每栋楼统一拉伸了 10 m**，136 m 的楼和 14.5 m 的楼在里面一样高。
CesiumLab 的 `model2tiles` 显然没有绑定 `high` 字段。

本模型使用真实的 `high`（3–136 m），高度信息是本模型相对既有白模的主要增量。

## 5. 怎么打开

**浏览器**（推荐）：双击 `start_viewer.bat`（起本地服务并自动开浏览器，用完关掉黑窗口即可）。
three.js 已放在 `vendor/`，**断网也能看**。

查看器操作：**左键旋转 · 中键平移 · 右键平移 · 滚轮缩放 · 双击或点「复位视角」回到初始机位**。
底部有「建筑 / 地形」显隐开关和 1–5× 垂直夸张滑块（模型跨度 10 km 而高度只有 200 m 量级，
想看楼的高度差把夸张拉到 3× 以上更直观）。

直接双击 `viewer.html` 会失败——浏览器禁止 `file://` 下用 fetch 读取本地 GLB，也禁止 ES module 加载。
这是浏览器安全策略，不是文件问题，必须走本地服务。

> ⚠️ 批处理必须是**纯 ASCII**。含中文的 `.bat` 在中文 Windows 上会被 cmd.exe 按 GBK 解析，
> UTF-8 字节变成乱码并可能被当成命令执行（报"'ｅ湪鍚姩鏈湴鏈嶅姟' 不是内部或外部命令"），
> 甚至会破坏后续行的解析导致 `cd` 失效、服务起在错误目录。本 `.bat` 已全部改为英文提示。

**Cesium**：把 `tileset.json` 与 `city_model.glb` 放同一目录，加载该 tileset 即可，
定位自动正确（变换矩阵已含 ECEF 定位）。

**Blender / 3ds Max**：导入 `city_model_zup.glb`，Z 轴朝上，单位米。

**其他**：任意 glTF 查看器（Windows 3D 查看器、gltf-viewer、model-viewer）都能开 `city_model.glb`。

## 6. 怎么重新生成

脚本在 `C:\Users\75268\Desktop\citymodel\`：

```
build_city.py      主流程: 读 shp+dbf+DEM → ENU → 三角化拉伸 → 导出 GLB/tileset/geojson
render3d.py        软件 z-buffer 光栅化渲染 (不依赖 OpenGL)
preview.py         matplotlib 平面图
est_geoid.py       垂直基准标定
```

运行：`python C:\Users\75268\Desktop\citymodel\build_city.py`
（约 11 秒，输出到本目录）

依赖：`numpy shapely tifffile trimesh pillow imagecodecs`

> ⚠️ 本机 Windows 版 Anaconda Python **无法接受含中文的脚本路径**——
> `python <中文路径>.py` 会静默退出（exit 127，无任何输出）。
> 脚本必须放在纯 ASCII 目录下，用 Python 内部的中文字符串访问数据文件。
> 同理，`Pillow` 解码本 DEM（16-bit LZW TIFF）会**硬崩溃**（访问违例，非异常），
> 必须用 `tifffile` + `imagecodecs`。

glTF 侧还有三个必须显式处理的点，`patch_glb_material()` 里一并做了：

1. **`NORMAL` 必须自己写**。trimesh 不导出法线，而 three.js 对缺失的法线属性取默认值 `(0,0,0)`，
   导致 `N·L ≡ 0`、直射光与半球光全部失效，模型**渲染成全黑**。顶点按面展开不共享，
   逐面法线就是精确的平直着色法线。
2. **材质必须显式挂**。glTF 规范给"无材质"图元套的默认材质是 `metallicFactor = 1.0`，
   在没有环境贴图的查看器里同样是黑的。已挂 `metallic 0 · roughness 0.85 · doubleSided`。
3. **不要走 trimesh 的 `visual.material` 通道**——它会把顶点色清零（COLOR_0 全变 `[0,0,0,255]`）。
   所以这里直接二进制改写 GLB 的 JSON chunk，改完用官方校验器验过：0 error / 0 warning。

另外颜色写成 `uint8` 时别忘了 **×255**：`np.clip(色值, 0, 1)` 之后直接 `astype(np.uint8)`
会把所有颜色压成 0 或 1，看起来同样是全黑。

**不要在查看器里加雾**。模型跨度约 10 km、相机距离约 10 km，任何"看起来合理"的雾
（例如 near=14000）都会把远处整片压成背景色。

## 7. 已知限制

- **无纹理**：这是几何白模，颜色是按高度算的顶点色。`影像/raster.tif` 是正射影像（约 2 m），
  可以给**屋顶**贴图，但**立面**在正射影像里被压缩/遮挡，贴不出真实立面。要实景立面需倾斜摄影或街景补数据。
- **LOD 级别为 LOD1**：平屋顶体块。无屋顶结构（楼梯间、水箱、坡屋顶）、无女儿墙、无退台。
- **地形 30 m**：适合大范围地形贴合，不足以表达精细地形。DEM 有 35.8 % 为 NoData（裁剪区外的角），
  这些位置不生成地形面；这些轮廓整体落在 NoData 区的楼，基底回退到形心附近 5×5 有效邻域。
- **`BASE_MODE=max` 的代价**：楼高以「轮廓内最高地面」起算，所以坡地上的楼在低侧会
  高出地形一个局部起伏量（中位 2.45 m，p95 8.52 m）——**天空线整体被抬高约 2.5 m**。
  这是"建筑不沉入地形"的必然代价；若更在意高度不失真而非可见性，改用 `centroid`。
  极少数跨在 29 m 陡坎上的楼（起伏 >20 m）在 `max` 下低侧墙裙会很明显。
- **单瓦片**：整个区域是一块，无 LOD 分层。区域跨约 10 km × 5.6 km，
  同一刚性变换下边缘相对椭球面有米级弧度残差。若要发布到 Web，建议按四叉树切分为多瓦片。
- **`high` 字段本身未经验证**：本模型忠实还原 `high`，若 `high` 本身有错（例如把层数当米、
  或个别异常值），模型会照搬。异常值建议对照 DOM/街景抽查。
